# 阶段 0 · 立项（想法 → 需求基线 + Go/No-Go）

> 把「一个想法」用方法链变成「可验收的需求基线」。三档做法不同，**方法链相同**（重档走全，轻档取前两环）。
> 方法依据：JTBD（Jobs-to-be-Done）、Kano、MoSCoW、RICE、QFD 质量屋、BDD/Gherkin、IEEE 29148（NFR）。

## 三档做法

| 档 | 做法 | 产出 | 人设闸 |
|---|---|---|---|
| 轻 | JTBD 一句话 + 功能清单 + 明确不做 | docs/requirements.md | 点头就做 |
| 中 | + MoSCoW 优先级 + 3–5 用户旅程初筛 + Non-goals | requirements.md | Restate + 优先级签字 |
| 重 | + 干系人 + Kano 定性 + RICE 定量 + 风险 + 量化指标 + NFR | requirements.md + DECISIONS.md | Go/No-Go + 指标签字 |

## 方法链（重档完整版，中/轻档按上表截取）

### ① JTBD —— 澄清（把想法重构为「工作 + 结果」）
把想法写成一句：给【谁】完成【什么工作】，以达成【什么结果】。
- 「结果」必须可测——"更快"不是结果，"3 分钟内完成"才是。
- ✅ 验收：owner 确认这句"工作 + 结果"就是他想要的（**停下来等签字，禁止跳过**）。

### ② 干系人（重档）
列出：谁提需求、谁拍板、谁用、谁受影响、谁验收。
- ✅ 验收：每条需求能指到"谁说的、为什么"。

### ③ Kano 定性（重档）
给每条需求标类：**基本型**（缺失即不满）/ **期望型**（越多越好）/ **兴奋型**（惊喜）。
- 用途：基本型优先保证，兴奋型优先可砍。
- ✅ 验收：每条需求标了 Kano 类别。

### ④ MoSCoW 优先级（中/重档）
Must / Should / Could / Won't。**Won't 必须写理由**（进 DECISIONS.md）。
- ✅ 验收：每条标优先级，Won't 有理由。

### ⑤ 定量排序（重档）：RICE 或 QFD 简化版
- RICE = Reach × Impact × Confidence ÷ Effort；或价值 vs 工作量矩阵。
- 风险 = 概率 × 影响（高/中/低）。
- ✅ 验收：需求按分数排序，**前 3–5 条 = 首批用户旅程**。

### ⑥ 可量化成功指标（重档）
不是"好用"，是"X 天内 Y 项闭环""错误率 < Z%""P95 ≤ __ms"。
- ✅ 验收：指标可测、有基线。

### ⑦ NFR（中/重档）
性能 / 安全 / 可用性 / 容量 / 合规，见 `references/stage-2-spec.md` 与 `templates/standard/specs/nfr.md`。

### ⑧ 落地：Given-When-Then（中/重档）
把首批旅程写成可测验收（Gherkin 三行），交阶段 2 定格为 spec.md。
```
Given 已登录管理员
When 填写资产信息并提交
Then 列表出现该资产、状态=在库
```

## 人设闸（owner 签字 3 个点）
① JTBD 复述（理解对吗）→ ② 优先级（Must/Should 认不认）→ ③ Go/No-Go + 成功指标。

## 失败处理
| 现象 | 处理 |
|---|---|
| JTBD 复述被否 | 再澄清，直到 owner 说对 |
| 优先级/指标不认 | 改到认，不硬推进 |
| No-Go | **停止**（这是胜利，不是失败——省下了后面所有浪费） |
