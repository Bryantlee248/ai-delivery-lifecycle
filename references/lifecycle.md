# AI Delivery Lifecycle · 生命周期骨架（9 阶段 × 3 档）

> 这是统一工具 `ai-delivery-lifecycle` 的**公共底座**：把「一个想法 → 一个合格产品」拆成 9 个阶段，
> 每阶段按**轻/中/重三档**决定做多深、上多少门。
> 三档整合了三个既有 skill 的优点：
> - 轻档 ← `codex-personal-project-starter`（紧凑循环、类型识别、docs 结构、API 设置、多用途警告）
> - 中档 ← `ai-requirement-to-ship`（spec/DESIGN/plan/tasks/converge/验收、垂直切片、机器门）
> - 重档 ← `enterprise-governance`（五文件 manifest、分权、批准链、CI diff 门、证据锚、L0-L3）
>
> 原则：**档位由风险触发，不由"最佳实践清单"触发；审计内核按档位比例启用。**

---

## 一、档位路由（打分制，带出处）

开工对 **5 个维度各打 0–3 分**（打分是人对事实的判断；映射是机械规则，不再靠感觉）。

### 打分表（每格有操作定义；末尾为参考依据）

| 维度 | 0 | 1 | 2 | 3 | 依据 |
|---|---|---|---|---|---|
| **数据** | 公开/合成 | 内部非敏感 | 个人/敏感数据（PII/凭据） | 受监管（医疗/金融/GDPR 特殊类别） | 企业数据分级 · NIST 800-60 · FIPS 199 |
| **环境** | 本地运行 | 内网/演示 | 生产（有真实用户） | 关键生产（需 HA/灾备/回滚演练） | dc-soc-sys 蓝图 L0–L3 |
| **失败影响** | 可重建无损失 | 损失工时 | 业务中断/数据损失 | 安全/合规事故、不可逆 | FIPS 199(Low/Mod/High) · ISO 31000 |
| **协作** | 单人单 agent | 单人+多 agent | 多人/多平台/外部组件 | 跨组织/多供应商 | dc-soc-sys 蓝图 |
| **合规审计** | 无 | 内部审计/留痕 | 外部监管/需报告 | 强监管+长期证据留存 | dc-soc-sys 蓝图 |

### 机械判定规则（OWASP「因子打分 + 阈值」模式）

```
重档：任一维度 ≥ 2
轻档：五个维度全部 = 0
中档：其余（有 ≥1，但无 ≥2）
```

> 取 **MAX 而非求和**：安全优先。一个高危维度（如"受监管数据"）就该上控制面，不能被其他维度的低分平均掉。

### 档位 → 治理等级（dc-soc-sys 蓝图 L0–L3）

```
轻档 = L0（无治理，紧凑循环）
中档 = L1（轻治理：AGENTS.md + decisions + 执行面门）
重档 = L2（控制面：五文件 + 分权 + 批准链）
       重档内再判：若 环境≥2 且（数据≥2 或 合规≥2）→ L3（生产/受监管）
```

### 打分示例

| 项目 | 数据/环境/影响/协作/合规 | 档位 |
|---|---|---|
| 一次性脚本 | 0/0/0/0/0 | 轻档 L0 |
| 资产台账练习（合成数据+内网演示+单人3角色） | 0/1/0/1/0 | 中档 L1 |
| 真实 SOC 生产（真实告警+生产+事故级影响+多人+强监管） | 3/3/3/2/3 | 重档 L3 |

> **轻档的紧凑循环**（不走完 9 阶段，是它的降级形态）：
> `澄清当下功能 → 最小切片实现 → UI/功能验证 → git 快照`。循环直到做完。
> 判断依据（codex 的克制原则）：**流程是护栏，不是产品**；出现"为了走流程而写文档"就退回紧凑循环。

## 二、9 阶段 × 3 档矩阵

### 阶段 0 · 立项（想法 → 值不值得做 + 定性定量）

**目标**：澄清需求、定性分类、定量排序、Go/No-Go 决策。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | 一句话定位 + 目标用户 + 核心价值（3 问） | README 几行 / docs/requirements.md | 人：点头就做 |
| 中 | Restate 确认 + 3–5 用户旅程初筛 + MoSCoW 优先级 + Non-goals | requirements.md（需求基线） | 人：Restate + 优先级签字 |
| 重 | 干系人分析 + Kano 分类 + RICE（价值/工作量）+ 风险=概率×影响 + 可量化成功指标 | requirements.md + DECISIONS.md（D-xxx 记录取舍） | 人：Go/No-Go + 指标签字 |

> 方法链（JTBD → Kano/MoSCoW → QFD/RICE → Given-When-Then → NFR）见 `references/stage-0-intake.md`。

### 阶段 1 · 治理（定档 + 事实入口 + 分权）

**目标**：建唯一事实入口、角色分权、分支保护、CI 门。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | git init（快照当回滚），不建治理 | .git | 无 |
| 中 | AGENTS.md（轻量入口）+ docs/decisions.md | AGENTS.md, decisions.md | 无 |
| 重 | 五文件（PROJECT.json + GOVERNANCE/ROADMAP/DECISIONS/WORKLOG）+ 分支保护 + CI + 角色分权 | 五文件 + .github/ + CI | 机器：validate 本地门绿 |

### 阶段 2 · 规格（what/why + UI + NFR）

**目标**：把"要什么"定格成可测验收 + UI 规格 + 非功能需求。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | 需求几行 + UI 大致样子（口头/草图） | README | 无 |
| 中 | spec.md（3–5 旅程 + 可测验收）+ DESIGN.md（UI 参照物） | spec.md, DESIGN.md | 人：Approval 签字 |
| 重 | 中档 + NFR（性能/安全/可用性/合规）+ Edge Cases + 契约 | spec + DESIGN + NFR + OpenAPI | 人 + 机器：converge 块单一事实源 |

### 阶段 3 · 架构（ADR + 契约 + 数据 + 边界）

**目标**：架构决策、接口契约、数据模型、组件/信任边界、分权声明。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | 技术栈一行（不写 ADR） | 无 | 无 |
| 中 | ADR（形态+技术栈+理由/代价）+ 接口契约 | ADR, OpenAPI | 人：架构评审（简） |
| 重 | 中档 + 数据模型/主权 + 组件/信任边界 + 威胁模型 + IWP（分权声明） | ADR + 契约 + IWP + file_ownership | 人：架构评审 P0–P3 |

### 阶段 4 · 计划（垂直切片分解 + 依赖排序）

**目标**：切成垂直切片（一条旅程端到端），排依赖，标单一事实源。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | 心里有数，直接做 | 无 | 无 |
| 中 | plan.md + tasks.md（垂直切片 + 单一事实源） | plan.md, tasks.md | 4 判据（端到端/全栈/独立演示/依赖隔离） |
| 重 | 中档 + IWP 绑定工作项 + file_ownership 路径 | 同中档 + IWP 分配 | 同上 + 分权一致 |

> **切片工具映射**：市场成熟工具 spec-kit 的 `/plan` + `/tasks`（137k★，可选中/重档集成）；本项目默认自研 plan/tasks 模板 + `converge.mjs` 对账（spec ↔ tasks ↔ 证据对齐）。工具是切片的生产手段，**converge 是切片质量的验收锚**。

### 阶段 5 · 实现（逐切片端到端 + 分权强制）

**目标**：逐切片实现（界面+逻辑+数据+权限+审计），实施方只在声明路径内写。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | 最小切片 + UI 验证 + git 快照（紧凑循环） | 代码 | 无 |
| 中 | 逐切片 dev-loop + 单测 + UI/E2E | 代码 + 测试 | converge 部分 |
| 重 | 中档 + CI diff 归属门（越权即拦）+ 未验收阻断 | 代码 + 测试 + 证据 | 机器：CI diff 归属 |

### 阶段 6 · 收敛与批准（机器对账 + 评审 + 批准链）

**目标**：机器对账（spec/tasks/DESIGN/测试/证据全对上）、评审、批准必须挂证据。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | git status 干净 + 功能跑通 | 无 | 无 |
| 中 | converge.mjs 对账绿 + verify.mjs | converge 绿 | 机器：converge |
| 重 | 中档 + R2 评审 + APPROVED 挂 approval | 评审记录 + 状态 | 机器：converge + 批准链 |

### 阶段 7 · 验收与验证（四关 + 独立验证 + 证据锚）

**目标**：集成/交接/真人 UAT/风险四关 + 独立复现 + 证据防漂移。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | 用户自己点一遍 | 无 | 无 |
| 中 | 集成关（浏览器走查）+ 交接关 + 真人 UAT | evidence/ | 人：UAT 签字 |
| 重 | 中档 + 验证AI 独立复现 + 证据锚（file:line+sha256） | verification + evidence_anchors | 人 + 机器：证据锚无漂移 |

### 阶段 8 · 部署与演进（声明环境 → 部署 → 运营 → 复盘）

**目标**：声明环境/组件、部署+回滚、SLO/告警/恢复、复盘、退役、变更登记。

| 档 | 做法 | 产出 | 门 |
|---|---|---|---|
| 轻 | 本地跑 / 打包分发 | 无 | 无 |
| 中 | 部署 + 基本验证 | 部署记录 | 人：验收 |
| 重 | L2/L3 声明 environments/components → 部署 → SLO/告警/恢复演练 → 复盘 → 退役 | 环境/组件注册 + 运行证据 | 机器：等级-对象一致 + 部署验证 |

## 三、门禁清单（可审计的骨架）

**机器门**（按档位启用，都是"不绿 = 没完成"）：
| 门 | 作用 | 档位 |
|---|---|---|
| converge.mjs | 规格/任务/测试/证据对账 | 中/重 |
| verify.mjs | 只看产物，堵自我美化 | 中/重 |
| validate-governance.mjs | 五文件 schema + 引用 + 状态一致 + 批准链 + 分权 + 证据锚漂移 | 重 |
| CI diff 归属 | 实施方只能改声明路径，越权即拦 | 重 |

**人设闸**（AI 不可替代，只有 5 个点）：
`目标/边界 → 定样子(DESIGN) → 高风险批准 → 验收(UAT) → 风险拍板`。

**审计判据**：任何新 AI 只读仓库，就能回答——
`现在什么状态？谁改了什么？谁批准的？证据在哪？证据有没有漂移？`

## 四、复用与幂等原则

1. **幂等**：每阶段可重跑，每步有"✅ 验收"判据，失败即停（不硬编）。
2. **按项目类型取技术栈/UI/验收/分发**：B/S、C/S、小程序、App、CLI 的类型专属映射见 `references/project-types.md`（技术栈 ADR / 组件库 / 验收方式 / 部署分发）。
3. **不绑领域**：资产台账、告警工具、任何产品都能套。
4. **平台无关**：pi / Claude Code / Codex 通用；CI 默认 GitHub Actions，GitLab 可对等改写。
5. **先改清单再改代码**：规格/清单是锚，代码随清单走，不许反着来。
